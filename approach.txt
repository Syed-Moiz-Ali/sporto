├── melos.yaml
├── apps/
│   ├── partner_app/        # For venue owners / tournament organizers

2. Implementation Plan1.Initialize Core Storage & Sync Engine:packages/core.Set up Hive for the local-first strategy. You need a dedicated sync engine that watches for network changes.Initialize Hive and register adapters (generated by hive_generator).Create a SyncQueue Hive box. When an action occurs offline (like a Referee updating a score), save the mutation payload to this box.Implement a ConnectivityBloc that listens to network status. When reconnected, iterate through the SyncQueue, push to the Cloud API, and clear the queue upon success.2.Define Domain & Data Models:Using Freezed + Json_annotation.Define immutable entities. For local-first, your models need both JSON serialization (for the API) and HiveType annotations (for local storage).Example for Referee App (Match Score):Dart@freezed
@HiveType(typeId: 1)
class MatchScore with _$MatchScore {
  const factory MatchScore({
    @HiveField(0) required String matchId,
    @HiveField(1) required int teamAScore,
    @HiveField(2) required int teamBScore,
    @HiveField(3) required DateTime lastUpdated,
    @HiveField(4) @Default(false) bool isSynced,
  }) = _MatchScore;

  factory MatchScore.fromJson(Map json) => _$MatchScoreFromJson(json);
}
3.Implement the Local-First Repository Pattern:Clean Architecture.In your Data layer, repositories should strictly follow the read/write flow you specified:Read: Always yield the Hive data first via a Stream. Then, fire an API call in the background. If the API returns new data, update Hive. The Hive box will emit a new state, updating the UI reactively.Write: Write the mutation locally to Hive immediately (optimistic UI update). Then, attempt the API call. If offline, log the request in the SyncQueue.4.Build the Partner App:apps/partner_app.This app focuses on venue and booking management.Features: Venue Dashboard, Booking Calendar, Financial Earnings.BLoC Structure:BookingBloc: Fetches bookings from BookingRepository (Hive first).VenueManagementBloc: Handles opening/closing slots.Local-First Use Case: If a Partner approves a booking while offline, mark it status: approved_pending_sync in Hive. Show it as approved in the clean UI, and sync it when connectivity returns.5.Build the Referee App:apps/referee_app.This app requires robust offline capabilities, as referees are often on the field with poor internet.Features: Match Schedule, Live Scoring Interface, Match Reports.BLoC Structure:MatchScoringBloc: Handles rapid increment/decrement events.Local-First Use Case: Every time a point is scored, write it directly to a local Hive box. A background worker should debounce these updates (e.g., every 5 seconds) and push the aggregated score to the live API so fans can see the live feed.6.Presentation & UI Assembly:Using ui_kit.Wrap your feature screens using BlocBuilder and BlocListener. Since you favor clean, minimalist UI/UX, centralize your buttons, cards, and bottom sheets in the packages/ui_kit.Keep the UI entirely ignorant of whether data is coming from Hive or the Cloud. It simply consumes states (Loading, Loaded, Error) from the BLoC.3. State Management Example (Referee Live Scoring)Here is how your BLoC interacts with your Local-First architecture for a critical feature like live scoring:Event: ScoreIncremented(teamId) is dispatched to MatchScoringBloc.Bloc Logic: The Bloc immediately emits a new state with the updated score (Optimistic UI update).Repository Call: The Bloc calls repository.updateScore(newScore).Data Layer (Hive First): The repository saves the new score to HiveBox<MatchScore>.Sync Logic: The repository attempts a dio.post('/match/score').If it fails due to network error, the action is logged to the SyncQueue.The UI remains uninterrupted. The referee just sees a fast, responsive minimalist UI.
